# Personal Research Portal — Research-Grade RAG

This repository implements a baseline Retrieval-Augmented Generation (RAG) pipeline over a local PDF corpus, with production-minded patterns for reproducibility, logging, traceable citations, and evaluation.

The system ingests PDFs into cleaned text, chunks them, embeds and indexes chunks with FAISS, retrieves top-k evidence chunks for a query, and generates an answer using a local LLM via Ollama. Answers include inline chunk citations (for example, `[S001::c00002]`) and a deterministic `References` section built from the manifest.

---

## The Streamlit portal (what you can do)

The UI is implemented in `src/app/`:

- **Search** (`0_Search.py`): retrieval-only (FAISS top-k chunks)
- **Ask** (`1_Ask.py`): retrieval + generation + citations + logging (threaded)
- **Threads** (`2_Threads.py`): browse past runs by thread; export thread summaries
- **Evaluation** (`3_Evaluation.py`): run the eval set and view metrics + examples
- **Artifacts** (`4_Artifacts.py`): generate and export an evidence table from a logged run

The portal reads/writes local files:
- reads: `data/chunks/chunks.jsonl`, `data/index/*`, `data/manifest/manifest.enriched.csv`
- writes: `logs/query.jsonl`, `logs/eval_summary.csv` (and related logs)
- optional exports: `outputs/` (if you choose “Write …” in the UI)

## Quickstart (fastest way to launch the UI)

### Preconditions (first time only)
1) Create the Python venv + install deps:
```bash
make setup
```

2) Install Ollama and pull the model:

```bash
ollama pull llama3.2
```

3) Build the local corpus index (required before asking questions in the UI):

```bash
make ingest chunk index
```

4) Launch the portal

```bash
make streamlit
```

Then open the local Streamlit URL printed in your terminal.

If Streamlit asks for an onboarding email the first time you run it, you can just press Enter (blank) and continue.

## Typical UI workflow (what to click)

* Search: try keywords / phrases, verify retrieval quality and relevant sources.

* Ask: ask a question; the system retrieves top-k evidence and generates a cited answer.

* Threads: review saved runs grouped by thread_id; export the thread summary.

* Artifacts: pick a run → generate an evidence table → export as Markdown/CSV/PDF.

* Evaluation: run the evaluation set and inspect metrics + representative failures.

## What this RAG does (pipeline behavior)

Given a question, the pipeline:

1. Retrieves the top-k most similar chunks from the corpus (FAISS vector search over sentence-transformer embeddings).
2. Generates an answer using a local model (`llama3.2`) constrained to the retrieved evidence snippets.
3. Validates citations: if the model cites chunk IDs not in the retrieved set, the system refuses to answer rather than invent citations.
4. Adds structured references: it appends a `References:` section containing the source metadata from the manifest for cited sources (references are constructed by the program, not generated by the model).

All runs are logged to `logs/` (queries, retrieved chunks, prompt IDs, outputs, and evaluation summaries).

## 4) Asking questions

### One-command query

Use the Makefile `query` target:

```bash
make query Q="What is OptiGuide and what problem does it address?"
```

What happens:

* Retrieves top-k chunks (`k=5` by default)
* Generates an answer using Ollama (`llama3.2`)
* Validates citations (refuses if citations are invalid)
* Appends a deterministic `References` section based on the manifest
* Writes a log entry to `logs/query.jsonl`

### Change the local model

Override the default model from the command line:

```bash
make query Q="..." OLLAMA_MODEL=llama3.2
```

(Replace with any model you have pulled via `ollama pull <model>`.)

## 5) Run logs and traceability (what to submit)

This repository produces two different categories of logs:

### A) Run log (required deliverable: “>= 20 queries with retrieved chunks and outputs”)

The required run log is:

* `logs/query.jsonl`

Each record includes:

* question text
* retrieved chunk IDs, scores, and evidence text snippets
* prompt ID and prompt hash
* generator status and settings
* citation validation results (allowed chunk IDs, cited chunk IDs, valid/invalid citations)
* final answer (including deterministic `References` when applicable)

Important joining note: the evaluation set uses query IDs like `D01`, `S01`, etc., but `logs/query.jsonl` does not currently store that ID. When mapping evaluation rows back to full run traces, join by matching the exact `question` string (or search the question text in `logs/query.jsonl`).

### B) Evaluation summaries (metrics only)

These files contain per-query metrics, not full evidence:

* `logs/eval.jsonl` — metric rows written by the evaluator (id, type, k, counts, precision, coverage proxy, stderr, exit code)
* `logs/eval_summary.csv` — the same metric rows in CSV format

Use these for reporting and aggregate analysis; use `logs/query.jsonl` for evidence and failure-case writeups.

## 6) Evaluating the system (>= 20 queries)

The evaluation query set is stored at:

* `data/eval/queries.jsonl`

Run evaluation:

```bash
make eval
```

Outputs:

* `logs/eval.jsonl` — per-query metric rows (not full answers/evidence)
* `logs/eval_summary.csv` — summary metrics per query (CSV)
* `logs/query.jsonl` — full traces for each evaluated query (answers + retrieved evidence)

### Metrics

The evaluation includes:

Groundedness / faithfulness (structural):

* invalid-citation count (must be 0; invalid citations are refused)
* citation coverage proxy: fraction of non-empty output lines containing at least one citation

Additional metric:

* citation precision: fraction of cited chunk IDs that are in the retrieved set

Notes on interpretation:

* Because invalid citations are blocked at runtime, citation precision is expected to be 1.0 for accepted answers; remaining failures are typically “missing citations,” “insufficient evidence retrieved,” or abstentions (“Not found in the corpus.”).
* Coverage proxy is line-based and the output may include a `References` block, which can mechanically reduce the proxy even when substantive claims are correctly cited. Use it as a diagnostic signal, and inspect `logs/query.jsonl` for the actual answer text.

### Artifacts and exports

The portal can export:

* Evidence table (Artifacts page): Markdown / CSV / PDF
* Thread exports (Threads page): thread summary exports

If you choose “Write …” in the UI, files are written to:

* outputs/

### How to inspect failures

1. Open `logs/eval_summary.csv` and identify low-performing queries (for example, low coverage proxy or zero citations).
2. Locate the corresponding full trace in `logs/query.jsonl` by searching for the exact `question` string.
3. Inspect:

   * retrieved evidence snippets
   * whether the system abstained (“Not found in the corpus.”)
   * whether the strict retry was triggered
   * which chunks were cited and validated

## Citation behavior and enhancement

This repo implements “Structured citations”:

1. Inline citations in the answer body: `[S###::c#####]` (chunk IDs).
2. Deterministic `References` section appended by the program from `manifest.enriched.csv`, not generated by the model.

Trust gate:

* If the model cites any chunk IDs that were not in the retrieved top-k evidence for that query, the system refuses rather than hallucinate citations.
* If the model produces an answer without valid citations, the system abstains with `Not found in the corpus.` and does not include references.

## Notes and troubleshooting

### Ollama is not running

If the Python code cannot reach `http://localhost:11434`, open the Ollama app or run a model once:

```bash
ollama run llama3.2
```

### Fresh corpus / changed PDFs

If you add/remove PDFs in data/raw/, rerun:

```bash
make ingest chunk index
```

### Hugging Face warning (unauthenticated)

You may see warnings about unauthenticated Hugging Face requests when sentence-transformers downloads embedding models. This is normal; adding a token is optional and only affects rate limits.

### Performance tips (Apple Silicon laptops)

* Use smaller `k` for direct queries (5 is usually sufficient) and larger `k` for synthesis queries (7–10).
* Keep the context window at 4096 unless you see truncation. Increasing it can slow generation and increase memory usage.
